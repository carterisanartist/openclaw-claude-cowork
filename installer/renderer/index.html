    Prerequisites

    We need a few things in place before we wire anything up.

    If something's missing, click the link, install it, then press Re-check.

    Paste the shared bot token

    Your admin created a single company bot in Telegram (via @BotFather) and gave you its token. Every employee uses the same token; each employee gets their own private chat with the bot.

    Why we need this

    Everything in this system flows through one Telegram bot. On the Claw host we bind it to channels.telegram. On the Claude side, the bridge talks to api.telegram.org as the same bot.

    The token is stored only in local config files (OpenClaw's on the host, Claude Desktop's on the user side) — never transmitted anywhere except api.telegram.org.

    Choose a model for OpenClaw

    Claw needs an LLM to think with. Pick a provider, pick a model, paste your API key. We hand the choice to openclaw onboard --non-interactive so it writes the right keys in ~/.openclaw/openclaw.json (and its models.json registry) using OpenClaw's own contracts — no shape drift, no broken upgrades.

    What this actually does

    We run openclaw onboard --non-interactive --auth-choice <provider> --skip-bootstrap --skip-health and inject your key via the documented env var (e.g. ANTHROPIC_API_KEY). OpenClaw writes its own provider config under models.providers.<id> and sets agents.defaults.model.primary to your choice.

    We then run openclaw models set <provider/model> to pin the default model and openclaw status --deep to confirm the gateway is healthy.

    Bind OpenClaw to the bot

    We'll add a channels.telegram block to your OpenClaw config so it logs into the company bot. OpenClaw requires numeric Telegram user IDs in its allowlist — usernames are silently ignored.

    Config file

    ~/.openclaw/openclaw.json

    What we write

    channels.telegram.enabled: true, botToken, allowFrom (numeric IDs), and dmPolicy.

    Reversible

    We back up the existing config before writing. Other Gateway settings are left untouched.

    Approve a Telegram pairing
    
            
    
              On dmPolicy: "pairing", the first time someone DMs the bot OpenClaw issues them a 3–8 character pairing code.
              Approve it here (or anyone in commands.ownerAllowFrom can run openclaw pairing approve telegram <code>) and they're in.
            
    
            
    
              
              
              
            
    
            
    

            
    
              How pairing works
              
    OpenClaw caches the pairing in the bot's state directory. Approving a code grants DM access to that sender for the lifetime of the pairing store. To remove access later run openclaw pairing revoke telegram <sender_id> or wipe the relevant entry from ~/.openclaw/agents/<agentId>/pairings/telegram.json.
    
              
    Codes expire one hour after issuance — if a pending code goes stale, have the sender DM the bot again.
    
            
    
          
    

          
    
            Manual fallback
            
    If anything fails in this installer, drop into a terminal:
    
            
    openclaw gateway install         # set up the daemon
openclaw gateway restart         # bounce the running gateway
openclaw status --deep           # live health + channel probes
openclaw doctor --fix            # try to repair common issues
openclaw pairing list telegram   # see who's waiting for approval
openclaw pairing approve telegram <code>

    Smoke test
    
          
    
            We'll send /ping through the chat and wait up to 45s for the matching pong back from OpenClaw. No LLM tokens are spent — this is a plumbing check, not a model check.
          
    
          
    
            
            
          
    
          
    
          
    
            What this actually does
            
    We send a single message tagged [req:setup-XXXX] /ping to your Telegram chat, then long-poll getUpdates for up to 45 seconds looking for any reply from a non-self sender. OpenClaw's built-in /ping command replies pong without involving the LLM, so this works even on a brand-new install with no provider key configured yet.
    
            
    If you don't see pong back: the most common causes are (1) the Gateway daemon isn't running on the Claw host, (2) your Telegram user id isn't in allowFrom, or (3) you're on dmPolicy: "pairing" and haven't been approved yet. Re-run the Claw-host side of this installer to fix any of those.
